1. CURRENT PRODUCT GOAL

LessonPlanner is a local-first native macOS teacher-planning application. It is a generic product shell, not a curriculum-specific repository.

The intended teacher workflow is:

1. The teacher chooses a local planning workspace.
2. The teacher imports all setup/planning documents in one place. Import should accept multiple files, DOCX/PDF, and whole folders.
3. The app identifies and sorts imported documents into likely roles on the back end: pacing guide, curriculum map, instructional calendar, assessment schedule, daily schedule, lesson materials, template, or other.
4. Readable content should be used automatically where possible. If a field cannot be read, the app should leave it blank or use a safe generic placeholder, then allow optional manual filling.
5. The app builds governing pacing/timing parameters from setup documents.
6. The app creates a weekly planning schedule for a set week.
7. Each scheduled lesson should link to the three main outputs:
   - lesson plan;
   - slide deck / PowerPoint;
   - differentiation guide.
8. A weekly check-in prompt/conversation should help the teacher adjust pacing naturally. If AI features are enabled later, this weekly check-in is the preferred place for conversational pacing refinement.

The long-term app must remain useful without generative AI. AI is an optional enrichment path, not the foundation.

5. IMPORTANT DESIGN DECISIONS AND WORKFLOW CORRECTIONS

Document intake should be streamlined:

- Previous direction had too much teacher review and approval per document.
- User feedback: this is cumbersome and unsustainable.
- Current direction: import documents and automatically port readable information into pacing and weekly planning.
- Missing/unreadable fields should be omitted, left blank, or safely autofilled where generic placeholders are acceptable.
- Manual fill-in should be available but not mandatory between import and weekly planner preview.

Weekly schedule is the central container:

- Final app should not produce isolated outputs only.
- The weekly planning document/hub is the container for the week.
- Each scheduled lesson should link to the three outputs: slide deck, lesson plan, differentiation guide.

Weekly check-in is the pacing adjustment surface:

- User specifically wants natural, conversational weekly check-in prompts.
- If AI is enabled later, the weekly check-in should modify/refine pacing through teacher conversation.
- The app should not silently rewrite governing pacing without teacher-visible acceptance.

Local testing profiles are for QA only:

- They simulate multiple users locally.
- They do not represent production accounts, cloud identity, sync, permissions, or admin infrastructure.
- Real login/user assignment will require larger infrastructure later.

Visual redesign approach (added Batch 007):

- When the owner supplies a design handoff, recreate it natively in the target codebase's own
  environment (SwiftUI here) — do not embed the handoff's HTML/CSS reference directly.
- For a redesign spanning multiple screens, propose a staged rollout (foundation + one screen
  first) and stop for visual confirmation before continuing to the rest, rather than
  redesigning everything before any feedback.
- Where the handoff specifies an asset the platform can't use natively as-is (a web font, a
  hand-drawn icon set), confirm the substitution strategy with the owner before implementing,
  rather than silently picking one.
- If a design calls for an interaction (e.g. a remove button) the data layer doesn't yet
  support, add the small supporting method rather than ship a decorative control that doesn't
  work — this is a natural extension of the approved work, not a new scope decision requiring
  a stop.


6. PROBLEMS ENCOUNTERED, ATTEMPTED SOLUTIONS, AND WORKABLE SOLUTIONS

Problem: User could not select multiple files during import.

- Attempted/identified issue: file picker was too restrictive and did not support the real setup workflow.
- Workable solution: document intake now accepts multiple files and folders, including PDF and DOCX.

Problem: DOCX files were not permissible.

- Workable solution: DOCX import was added and tested.

Problem: Document-by-document teacher approval was too cumbersome.

- Attempted direction: approval/readiness gating around imported documents.
- User feedback: process is unsustainable.
- Workable solution: remove document approval gate; use readable documents automatically; allow optional manual correction/fill-in for blanks.

Problem: 29 imported documents appeared imported, but only one science lesson appeared in planning preview.

- Cause direction: imports were not fully auto-syncing into course pacing / weekly planner.
- Workable solution: readable setup documents now create starter course pacing, approved lesson placeholders, and weekly planner assignments; existing readable imports can backfill on app/profile load.

Problem: Weekly planner showed non-obvious setup requirements and no scheduled lessons.

- Workable solution: document intake and readable imports now auto-build more of the planning scaffold; weekly planner messages were adjusted away from requiring hidden setup steps.

Problem: Weekly planner initially used a long list layout instead of a true weekly schedule.

- User provided a desired weekly lesson plan layout/reference.
- Workable solution: weekly planner was changed to a compact table with time rows and weekday columns.

Problem: Only the 9:00 AM block initially populated.

- Cause direction: daily schedule information was not governing placement strongly enough.
- Workable solution: imported daily schedule documents now map lesson subjects to schedule-derived blocks.
- Current observed/default mappings from sample packet:
  - English -> 8:35 AM–9:35 AM
  - Math -> 9:45 AM–10:45 AM
  - Science / Social Studies -> 10:45 AM–11:15 AM
  - Art / Specials -> 12:30 PM–1:10 PM
- Existing stale 9:00 AM assignments can be repaired on reload after schedule import.

Problem: Weekly cells looked noninteractive.

- Workable solution: lesson cards are clickable; Plan/Deck/Guide controls generate/open outputs; Edit/Remove actions appear on each card.

Problem: Weekly planner cell-flow problems and huge blank bands.

- Cause direction: time rows expanded based on the busiest cell, creating awkward whitespace across the grid.
- First attempted fix: bounded weekly table cells with internal vertical scroll areas.
- Second attempt, 2026-07-28: fixed-height time rows (176pt), internal scrolling for
  overloaded cells, wider day columns, compact lesson cards, and Plan/Deck/Guide/Edit/
  Remove controls on a tighter row.
- Why the 2026-07-28 fix was not sufficient: a fixed row height trades one problem for
  two. Cells holding two or more lesson cards clipped the second card mid-way, cutting
  off its Plan/Deck/Guide controls, while rows holding zero or one card still consumed
  the full 176pt and left large empty bands. The nested per-cell ScrollView also captured
  scroll-wheel events away from the surrounding grid and hid the clipped content with no
  visible affordance.
- Workable solution as of 2026-07-29 (Batch 001) — INTRINSIC ROW HEIGHT:
  - Metrics.rowHeight (fixed 176) became Metrics.minRowHeight (a floor of 88);
  - each row's HStack takes intrinsic height via .fixedSize(horizontal: false, vertical: true),
    so the row is exactly as tall as its tallest cell;
  - WeeklyPlanningTimeCell and WeeklyPlanningTableCell take a minHeight instead of a
    height and use .frame(minHeight:maxHeight:.infinity), so every cell border stretches
    to the row height and the grid lines stay aligned;
  - the nested per-cell ScrollView and LazyVStack were replaced with a plain VStack, so
    nothing is clipped and the scroll wheel reaches the surrounding grid again.
  Visually confirmed 2026-07-29 (Batch 004) against the pre-fix baseline screenshot
  (Design Screenshots/2026-07-28/07-this-week-cell-flow-compact.png): crowded cells fully
  visible, sparse rows collapsed instead of holding a blank band, grid lines still aligned.

Problem: the weekly grid created a separate time row for every distinct start time.

- Workable solution as of 2026-07-29 (Batch 003): slot identity now lives in one pure, tested
  type, Sources/LessonPlanner/WeeklyGridLayout.swift, which clusters start times within a
  15-minute tolerance (anchored on the first start in each cluster, so drift can't chain
  multiple nearby starts into one row). 8 tests cover it.

Problem: Screenshot capture of whole display was unsafe.

- Attempted solution rejected: full-screen `screencapture`.
- Reason: could capture unrelated sensitive screen content.
- Workable solution: window-only screenshot capture using the LessonPlanner window ID. This produced safe app-only screenshots.

Problem: macOS UI automation through System Events failed.

- Error: `osascript is not allowed assistive access. (-1719)` (or `-1728` depending on call site).
- Workable solution: add capture-only launch environment flags so the app opens directly to a selected tab without UI clicking (LESSONPLANNER_DESIGN_CAPTURE=1, LESSONPLANNER_INITIAL_TAB=...). For window-ID screenshot capture specifically, System Events is not needed at all — see the next problem.

Problem: `screencapture -l <windowID>` failed with "could not create image from window" (blocked visual QA across several earlier sessions).

- Cause: the target window was not frontmost/on-screen yet.
- Workable solution, found 2026-07-29 (Batch 004): run
  `osascript -e 'tell application "LessonPlanner" to activate'` first — a plain Apple Event,
  not System Events, so it needs no Accessibility permission. After that,
  `CGWindowListCopyWindowInfo` reports the window `onscreen=true` and
  `screencapture -l <windowID>` succeeds. When multiple same-bundle-ID processes are running
  (e.g. a stuck old instance), this `activate` call is also more reliable than generic
  app-launcher tools for bringing the *correct* (most recently launched) instance forward.

Problem (Batch 007): `computer-use` clicks immediately followed by typed text sometimes all
landed in the field that was focused *before* the click.

- Cause: the click and the following `type` action were outrunning SwiftUI's AppKit
  focus-change timing — the synthetic keystrokes arrived before first-responder status had
  actually moved.
- Workable solution: insert a short `wait` (~0.3s) between a `left_click` that changes focus
  and the `type` that follows it.

Problem (Batch 007): a SwiftUI TextField's placeholder text ("Add a task") appeared to read as
something else ("Id a task") in a screenshot.

- Cause: the blinking text-insertion caret visually merged with the first letter of the
  placeholder at that instant. Not a real rendering bug.
- Workable solution: re-screenshot after the field loses focus (or after the blink cycles)
  before concluding there's a genuine text-rendering defect.


7. CURRENT LIMITATIONS

- Visual PDF content, handwriting, diagrams, and some fraction/equation formatting are not reliably extracted. OCR/math/diagram understanding remains a future source-quality pipeline.
- Weekly package generation can create/link missing outputs, but OS-level notifications are not implemented.
- Visual redesign ("Sunrise Planner") is code-complete across all 5 screens as of Batch 023.
  Workspace, the final screen, is built/tested/self-verified but still awaiting the owner's
  visual sign-off. See section 4 and section 13.
- Weekly planner rows size to their tallest cell, so nothing is clipped and sparse rows collapse. Very dense cells will make a row tall; if that becomes a problem the answer is a different overflow pattern (collapsed cards with click-to-expand, a detail drawer, or an agenda view), NOT a return to fixed row heights.
- Local teacher profiles are test scaffolding only, not real accounts. Real login, user assignment, cloud sync, permissions, and admin roles are future infrastructure work.
- Native PowerPoint exporter is functional but generic/minimal. It does not yet preserve or fill real customer-owned PowerPoint layouts — `PowerPointTemplateInspector.resolvePlaceholders(url:)` (Batch 005) is a prerequisite building block for that, not yet consumed by the exporter itself.
- Template placeholder-inheritance resolution is scoped to `<p:sp>` text placeholders; picture/graphicFrame placeholders are not resolved (documented, not a bug). It does not perform visual fidelity QA. The on-screen "Placeholder inheritance" list (Batch 006) has not been visually confirmed against a real customer-owned `.pptx` — this project's own generated decks never populate it, since they don't use placeholders at all.
- Google Slides is supported through PowerPoint upload/conversion testing, not a native Google Slides API integration.
- No school curriculum, student data, or proprietary templates should be embedded in product code or tests.
